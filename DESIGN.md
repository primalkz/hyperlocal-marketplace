# design

building a hyperlocal grocery marketplace. three portals (vendor, customer, admin) on one express api. keeping notes on the non-obvious bits so i can defend them later.

## layout

two apps in one repo. backend/ is express + prisma, frontend/ is next.js. i kept them apart because the assignment grades the backend and i wanted it to stand on its own. a single next.js full-stack app would ship faster but hides the backend inside route handlers.

backend layout, one concern per file. src/app.ts wires express, src/server.ts is the listen entry for local and render, the routes/ files are thin transport, logic sits next to the prisma calls. no service layer abstraction; the routes are short enough that a layer on top would just move code around.

## users

one table with a role enum (vendor, customer, admin). considered splitting into three tables. did not, because the data is the same shape (email, hash, role) and a role check is one comparison. a vendor with no shop yet, or a customer who never orders, is still just a row.

## shop approval

shops have a status: pending, approved, rejected, disabled. a vendor registers and creates a shop, it starts pending. admin moves it to approved or rejected, and can disable later. customers only ever see approved and not-disabled shops. a rejected or disabled vendor can still log in (so they see why) but every mutation returns 403, via a small assertActive check in the mutating handlers.

## cart pinned to one shop

one cart per customer (cart.customerId is unique). cart.shopId is nullable and only set once the first item lands. adding a product whose shop differs from the cart's shop returns 409. i chose 409 over silently clearing because a silent clear loses the customer's selection with no feedback, and that is worse than asking them to clear it.

cartItem has a unique on (cartId, productId) so adding the same product twice just bumps quantity, via an upsert. no read-then-write.

## orders snapshot their items

orderItem stores productId but no foreign key to product, and copies title, image and price in. an order is a record of what was bought at the time. if a vendor renames or deletes a product later, past orders must not change. deleting a product still cascades off the cart (live state) but never off an order.

## checkout is one transaction

place order reads the cart, sums the total from live product prices, writes the order and items, then deletes the cart items and nulls the cart's shopId, all inside prisma.$transaction. if any step fails the cart stays intact. the cart is not deleted, just emptied, so the customer keeps the same cart row.

## distance in node not sql

nearby shops is haversine computed in node after fetching approved shops. for a handful of shops this is simpler than a raw sql function and i can unit test the formula. for real scale i would push it into a sql function or use postgis. noted in the readme.

## auth

bcrypt (10 rounds) for passwords, jsonwebtoken (hs256, 7d) in an httponly cookie. the cookie is samesite lax in dev and none + secure in production, because frontend and backend are on different domains in prod and lax would block the cookie on cross-site fetch. cors is locked to client_url with credentials. i read the cookie header by hand instead of pulling cookie-parser; it is four lines and one less dependency.

verify pins algorithms to hs256 so an alg-confusion attack does not work. /auth/me only returns the session (userId, role), never the email, so a leaked token leaks as little as possible.

## not yours is 404

when a vendor hits a product that is not theirs, i return 404, not 403. a 403 would confirm the id exists. a 404 does not leak that. same for cart items that are not yours. the cost is that a real bug looks like not found, but the ownership check in code makes the real cause easy to trace.

## prisma singleton

globalForPrisma trick so tsx watch does not open a new client on every reload and exhaust neon connections. standard, one file.

## deploy

vercel deploys express with zero config if a recognized entry exports the app as default. src/app.ts has `export default app`. src/server.ts stays for local and render. prisma client is generated by the @prisma/client postinstall at build time, so the linux engine is right for the serverless runtime.

## things i did not do

- no rate limiting. would add express-rate-limit and a small ip+route window.
- no refresh tokens. the 7d access token is enough for this scope. a refresh flow would add a refresh_tokens table and a /auth/refresh that rotates it.
- no openapi. a markdown table is the api doc. openapi is nicer for codegen but heavier; i would add it if the api grew.
- no pagination on product and order lists. fine at this scale; would add cursor pagination past a few hundred rows.
